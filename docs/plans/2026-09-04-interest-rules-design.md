# Sprint 3：兴趣与规则设计

## 目标

让本地单用户可以维护一份当前兴趣档案，为后续推荐评分提供明确、可编辑、可解释的输入。用户填写兴趣描述、正向规则和负向规则后，系统保存到现有 `interests` 表；本轮不计算推荐分数，也不自动改写规则。

## 取舍

- 复用现有 `interests` 表，不新增数据库迁移。
- MVP 只维护一个“当前兴趣档案”：读取时取 active 记录，保存时更新它；不存在则创建。
- 规则使用一行一条的短文本，服务端 trim、去重、限长（每组最多 20 条），避免把自然语言直接当作查询语法。
- `description` 记录用户的整体偏好，正/负规则分别表达希望多看和明确回避的信号。
- 不接云端 AI，不自动从仓库分析反推兴趣，不影响已有仓库状态和来源证据。

## 数据流

`InterestWorkbench` 首次加载 `GET /api/interests`；保存时提交规范化后的 `PATCH /api/interests`。领域层负责读取 active 记录、规则归一化和事务写入，Route Handler 只做参数校验与错误映射。后续 ranking 模块读取同一份领域接口，并将命中的规则写入推荐理由。

## UI 状态与交互

- loading：表单骨架和 `aria-busy`。
- empty：说明当前没有档案，展示默认字段和“保存兴趣档案”主操作。
- editing：规则输入框按行编辑，保存按钮有 disabled/loading 状态。
- saved：显示“已保存”提示和更新时间，不清空表单。
- error：保留用户输入，展示可重试错误，不回滚到旧值。
- 所有输入、按钮和规则预览都提供键盘焦点样式；负向规则使用克制的警示色，不制造误导性的“硬过滤”承诺。

## 验收

- 单测覆盖空档案、创建、更新、规则 trim/去重/数量限制和读取 active 记录。
- API 拒绝非 JSON、超长或空规则异常输入，并返回稳定错误码。
- `lint`、`typecheck`、`test`、`build` 和现有 E2E 通过。

## 后续切片

下一步将基于结构化分析和兴趣规则实现可解释评分，再接 `keep/try/adopt/dismiss/block` 反馈事件；评分必须保留命中的正/负规则快照。
